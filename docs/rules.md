# Rules for porting an Amateur Surgeon game

These are the rules every port in this workspace follows. They were set while rebuilding Amateur Surgeon Christmas from its Flash original, and they hold for AS1, AS2, AS3 and anything after.
- Where the rules and the code disagree, fix the code.
- Where the rules are silent, follow what Christmas does (see [christmas.md](christmas.md)), then write the new rule here.

The technical description of the engine is in [engine.md](engine.md), and the plan and where it stands in [plan.md](plan.md); this page says what must be done and why.

## 1. One engine for every game

**The engine, Bleed Engine, is the same for every Amateur Surgeon port:**
- **What it is.** Its parts are `port/src/core`, `platform`, `engine`, `flash` and `surgeon`: package loading, vector art, the script runner, the stage, Flash's classes, sound, input, the debug menu, the test hooks and its splash ("Powered by Bleed Engine", before every game's own screens).
- **Shared, not copied.** Every game runs on that one copy. There is no per-game fork of it, no `#ifdef` per game, and no game name inside it.

**A feature a game needs is added to the engine, generally.** If a port needs something the engine cannot do (a Flash class, an event, a filter, a kind of clip, an IPA node), it is added to the engine as a general feature, working for any game that uses it. It is then documented in [engine.md](engine.md). Examples already made this way:
- the `SharedObject` save format with key renames;
- `transitionTarget` (the variable a game's transitions set);
- modules that replace or add to a clip;
- unnamed-clip `_parent` chains;
- filters.

**No game script is hard-coded.** A game's own logic and data live in its package and in its modules, never in the engine:
- **Run as data.** The game's scripts run from its script index: menus, story, transitions, banners, save, sounds, button handlers, frame scripts.
- **Not rewritten in C++.** Do not hand-write a screen, a menu flow, a sound table, a save layout or a frame's effects that the original's scripts already describe.
- **Not lists in code.** Do not write per-game lists of what a script did (a frame's variables, a clip's random frame, a repeat count) when the script itself can run.
- **The only per-game C++:**
  - the game's set-up function (its package, its save file name and key renames, its transition variable, its module registrations, its bindings);
  - its native modules, for scripts that are real game logic (an operation);
  - for an IPA game, its classes mirrored from the binary (below);
  - its additions the players asked for, which the original does not have (§7).

  Each module is registered for a sprite (`StageScreen::addModule`) and named in the package's `data/modules.json`.
- **Generated data is regenerated.** Data a tool generates from the scripts (`data/gamedata.json`) is regenerated by that tool, never edited.

**Hybrid games use the same engine.**
- AS2 is built from its IPA with pieces of its Flash original; AS3 from its IPA alone (it has no Flash original), on the engine's cocos layer (`src/engine/cocos`).
- **An IPA game's code.** Its game, decompiled from the iOS binary, is mirrored class by class (AS2's `src/as2`, the original's class names kept): that is its native code, as a Flash game's modules are. It runs on the engine's platform, recorded drawing and UIKit layer; whatever general it needs (views from nibs, AAC music, system fonts, the pass length, vector art for its Flash pieces) is added to the engine.
- **Its Flash pieces** are the Flash original's art drawn by `VectorArt`, their behaviour ported from the Flash scripts into the mirrored classes.
- Its content goes into the same package layout (§3).

## 2. What a port is

**A native game, Windows first**, built with the workspace's toolchain (llvm-mingw, SDL3, OpenGL, miniaudio), statically linked apart from `SDL3.dll`, shipped as `dist/<game>/` (the exe, `SDL3.dll`, `assets/`).

**Bleed Engine is multiplatform.** AS2 also builds for Android ([port.md](port.md#building-and-running)); more mobile ports are to come, so:
- **Portable shared layers.** No Windows-only API in the shared layers where SDL3 has a portable one; what differs per platform sits behind a platform call (`platform/`): AAC and movies (Media Foundation on Windows, the NDK's media codecs on Android), fonts (`systemFont`), texel order (`toTexelOrder`), whether there is a pointer (`touchDevice`). Game code calls GL 1.x, which runs as OpenGL ES 1.1 on Android (`platform/GL.h`).
- **Device inputs kept.** An input only a device had (tilt, shake, touch) is kept in the platform layer for devices that have it, and a PC gets a natural equivalent. AS2's torch follows the tilt on a device with an accelerometer and the pointer on a PC; its shake is the accelerometer's on a device and a hard shake of the mouse on a PC.

**Not a Flash emulator.**
- No SWF bytecode is run, and there is no Flash player or AVM.
- The original's ActionScript is decompiled (JPEXS FFDec), parsed, and its statements are translated into data actions the engine's runner executes, on the engine's own scene.
- What the runner cannot do, or what is real game logic, is native C++.
- The movie's symbols are vector art the engine draws.

**From its own original only.**
- A game rebuilt from its Flash original takes everything from that SWF and its scripts: art, sounds, transitions, particles, animations, rules, timings.
- Another version of the game (the iOS app of a Flash-sourced game) is not a reference.
- A hybrid (AS2) uses exactly the sources its plan names for each part.

**Online services are removed**, not ported: high-score servers, Adult Swim score submission, OpenFeint, Facebook, Twitter, links to web pages.
- Statements that call them are assigned to the package's `removed` module (§4).
- Their buttons and labels are hidden.
- `getURL` and `fscommand` do nothing.

**A player's progress is never lost.** A port keeps reading the save files earlier builds of it wrote. Christmas's SharedObject is kept as the `christmas_save.txt` its hand-made screens wrote, its levels renamed `grade<n>`.

## 3. Assets: extraction and categories

A game's content is one folder, its **package**: `port/games/<game>/`. It is the game's `assets/`: the exe finds it next to itself or in the source tree, and the dist target copies it.

**Extracting a Flash movie: `extract_swf <movie.swf> <package dir>`.**
- **Built from the SWF.** The build runs it from the original SWF (kept under `re/flash/`, never shipped).
- **Its output.** It writes `library.json`, `vector/` and `audio/`, and replaces them on every run. It leaves the package's own `data/` and `scripts/` alone.
- **Round trip.** It must read back exactly: it reads the package back, writes it again and requires byte-identical files, or it fails.
- **Art identical.** A change to the package format must also leave the art pixel-identical: a symbol sweep (`AS_VECTOR_SYMBOL`) and screen shots before and after, compared in RGB.

**Categories** (the layout is fixed; a new kind of content gets its own folder here, documented in [engine.md](engine.md)):

| Path | Holds |
|---|---|
| `library.json` | stage size, frame rate, background, Flash version; linkage names → ids; every shape, morph, sprite and font id |
| `vector/shapes/<id>.svg` | each shape, in the SVG dialect (valid SVG any browser shows; exact twips, gradients, strokes, style layers) |
| `vector/morphs/<id>_start.svg`, `_end.svg` | morph shapes, matching path order |
| `vector/symbols/<id>.json` | each sprite's timeline (`0.json`: the main one): place/move/remove, names, masks, colour transforms, filters, labels (lower case), frame actions |
| `vector/buttons.json`, `texts.json`, `edittexts.json` | buttons' records; static and edit texts |
| `vector/fonts/<id>.json` | metrics, codes, advances, glyphs (SVG) |
| `audio/<name>.mp3` / `.wav`, `audio/index.json` | each sound by linkage name; MP3 kept as stored (gapless: the seek samples and sample count in the index) |
| `scripts/` | FFDec's export of the movie's ActionScript (`frame_N/`, `DefineSprite_<id>/frame_N/`, `DefineButton2_<id>/`, `__Packages/`) and `index.json` |
| `data/` | the game's own data, in the source tree: what the original loaded from a server (Christmas's `dialogue.xml`), `modules.json`, data generated from the index (`gamedata.json`) |
| `images/`, `anim/`, `models/`, `video/` | IPA content (`extract_ipa.py`'s categories), for the hybrid games |

- **Vectors only.** A Flash game's art is drawn from its vectors at the size it appears on screen: never pre-rendered bitmaps, never video.
- **Loading.** A package is read at start (Christmas: about 0.35 s). The preloader target is under 2 s.

## 4. Scripts: decompiling, indexing, porting

**Decompile and index.**
- `port/tools/index_scripts.py <game> --swf <movie.swf>` exports the scripts with FFDec into the package's `scripts/`.
- `index_scripts.py <game> [--report] [--diff <other game>]` parses every one (`port/tools/as2.py`). Every script must parse, and print back to the same tree.

It sorts each statement:
- **Translated:**
  - timeline control on any target;
  - sets of variables and properties;
  - `if`, loops, `for..in`, `break`/`continue`/`return`, `delete`;
  - calls (the scripts' own functions, the engine's classes, a module's natives);
  - `new` of Flash's classes;
  - functions and handlers whose bodies are all of these.

  Literal data (missions, injury types, dialogue lines) is translated too.
- **Native:** what the runner cannot do (`switch`, `with`, `try`, a computed class...), and whatever a module claims.
- **Unported:** native with no module. **A port is not done while anything is unported.**

**Assign native code: `data/modules.json`.**
- **Fields.** Each module has its `impl` (the C++), what it is about, and what it takes:
  1. `matches` (regexes over a statement's source: those statements are forced native: the `removed` module takes online calls and the context menu this way);
  2. `patterns`;
  3. `functions`;
  4. `buttons`;
  5. `frames` (`"sprite:frame"`);
  6. whole `sprites`.

  The first that matches wins.
- **Takeovers.** A module that takes over a clip (the operation) owns that sprite: its scripts do not run on the stage.

**The report is the checklist.** `--report` lists:
- the counts;
- the `_root` variables the scripts use;
- the screens (main timeline labels);
- the functions called;
- the sounds;
- the native statements per module, and every unported one.

For a new game, read it before writing any code, and make it say 0 unported.

**Reuse before writing.** `--diff <other game>` compares every function both games define. Functions that are the same reuse the other game's module code; changed ones are ported as differences.

**Porting a native script to C++:**
- **Names.** Keep the Flash names (`BuildLevel`, `CheckTongs`, `RemoveInjury`) and structure, so the code reads against the script.
- **Unclear source.** Port what Flash made of the script, checked in FFDec's p-code when the decompiled source is unclear or garbled ("unpopped" values, `gotoAndStop(undefined)`).
- **Faithful quirks.** Keep behaviour that changes play, even if it was a bug (§7), and mark it in a comment.
- **One state.** Share state with the scripts through bindings (`Scene::bind`), not copies: a `_root` variable both use is one C++ field.
- **Sounds.** Play sounds through the game's own sound functions (`SoundBank::Scripts`), so the scripts' mute switches and volumes apply.
- **Saves.** Write progress where the scripts keep it (their `_root` variables and SharedObject, then `flush`), as the original's code did.
- **Module order.** Run a module's per-frame code as the clip's `onEnterFrame` ran.

**Data generated from scripts** (missions, types, lines) is written by a tool from the index (`flash_data.py`) into `data/`, and read at start; it is never compiled in and never hand-edited.

## 5. Running a game: the stage

A game runs on `StageScreen`: the main timeline is the screen, its scripts run from the index, Flash's classes are the engine's (`FlashClasses`), and modules plug in. Set-up per game (§1) and nothing else.
- **Modules** replace a clip (drawn in its place between the timeline's pieces; given to the scripts as that clip's name; its scripts not run) or add to it (drawn over it, with their own buttons and keys first).
- **Transitions** are the movie's own clips and scripts (Christmas: `ftb`, `bandage`). Game code changes screens by calling those functions on `_root`, never by swapping screens itself.
- **Text fields** show their variables from the scripts.
- **Buttons** run their handlers with Flash's events and `this`.
- **Sounds** are the scripts' `Sound` objects (gapless loops; no restart over themselves).
- **Saves** are the scripts' `SharedObject`.
- **Art is made ahead**, so nothing rasterises on screen:
  - a second of the stage's own playing (clips the scripts set playing included);
  - the frame a transition goes to;
  - an operation's stages.

  Filtered art that changes stands in with its last version while the new one is made.

## 6. Flash's semantics the engine keeps

Found the hard way; every one is load-bearing:
- **Instances.** A Flash instance is its (depth, placed frame, character) chain. A clip placed anew is a new instance, even with the same character and name: its variables, hidden or moved looks, playheads and per-piece state go with it. A clip that leaves the stage (its depth emptied, or its timeline gone past the frames that place it) is gone: placed again on the same depth and frame, it has the same chain but is a new instance, and its frame scripts run again from frame 1 (`Scene::prune` drops what an update no longer meets; kept, the level select gone back to after a patient never set its grade marks again, and they played through all their frames).
- **`for..in` over a clip** meets its children newest first (placed on a later frame, then the deeper), unnamed ones too.
- **Frame labels** are case-insensitive. A `goto` to a label a clip lacks leaves it where it is.
- **`hitTest(clip)`** compares bounding boxes, and `getBounds` counts hidden pieces.
- **NaN positions.** `_x` or `_y` set to NaN is ignored.
- **When frame scripts run.**
  - A clip's frame script runs after the code that attached the clip or moved it there.
  - What such a script sets on `_root` from inside an operation applies at the end of the pass.
  - A script that moves a timeline has the new clips' first-frame scripts run in the same pass, before anything plays on.
  - On a frame, the parent's script runs before its children's.
  - **A clip's own frame 1 always runs, even if the engine is slow to notice it.** A nested clip with no part of its own (`ArtNode::part`) has no playhead of its own: it is found each pass by a frame computed from its parent's (age since the parent reached its placement frame). Once the parent itself settles on a frame, that computation keeps advancing forever (the parent's own time-on-frame keeps growing), so the engine's first sight of the clip can already be well past frame 1 — as if Flash had skipped running it. `Scene::enter` runs frame 1 first the first time any clip is seen at all, regardless of what frame the age computation first reports, so a `gotoAndStop` meant to pick the clip's content on its very first frame still gets to run.
- **Markers.** The plain `stop`/`play`/`goto` the art already plays (frame markers) are not run again by the runner.
- **`gotoAndStop`/`gotoAndPlay` always take effect**, even when given a frame number or label that does not resolve (`undefined`, a label the symbol lacks, `NaN`): Flash still stops or plays the clip, just without moving it. `SceneClip::gotoFrame` falls back to the clip's current frame rather than doing nothing, so a clip meant to be held in place by such a call is not left to play on by itself.
- **Comparisons.** `a <= b` is `!(a > b)`, so a comparison with `undefined` or NaN is `undefined`, and `undefined <= 0` is true. `undefined == false` is false.
- **Bare names in a function** belong to the timeline the function was defined on, not `this`.
- **An unnamed clip's `_parent`** is the innermost clip holding it, unnamed ones included.
- **Clips act on their parents.** Child scripts acting on their parent (`_parent.gotoAndStop(1)`, `_parent.removeMovieClip()`) are run, not imitated.
- **A clip a script moves** starts what its new frame places at that moment (part clocks).
- **Random picks** are per instance and fixed.
- **Filters** (blur, glow, drop shadow) are sized in stage pixels.
- **A no-argument `stop`/`play`/`gotoAndStop`/`gotoAndPlace` is parsed as timeline control, even on a `Sound`.** `Sound.stop()` has no arguments, the same shape as `MovieClip.stop()`, so it is indexed as one of the timeline actions, not a call. The runner falls back to the target's own host (`Sound`, `XML`...) when it is not a clip, instead of silently doing nothing — the cause of a `mysound.stop()` inside a `stopme()` function never actually stopping the sound.

## 7. Fidelity: what to keep, what to change

- **Keep** every behaviour of the original that changes play (a scorpion dying after three saw hits, the lighter melting ice at a touch), with a comment saying it is the original's.
- **"Faithful to the original" is no excuse for a bug.** What a player sees as broken is fixed, even where the original's script did it (a quirk of the Flash player, a piece out of reach under the HUD, a stage that cannot be finished), and the fix is said in the docs and the code. Where the right behaviour is unclear from the original, another version's game logic may be read (never its images or baked art): Christmas's iOS port, AS2's Flash AS2 against its IPA. Behaviour no one reported as broken is left as the original has it. Christmas's SWF is version 8, where `undefined` converts to `NaN` as a number (not `0`, as version ≤6 did): `if (_parent.rando == 0) { _parent.rando = random(n) + 1; }`, used throughout for a piece's random variant (blood, staples, drops, the bandage wipe's confetti), never actually randomises, in the original either — `rando` stays `undefined`, the condition is always false. Every such piece sits on its first frame always; that is the original's own behaviour, not a port gap.
- **Fix** what only broke the screen or the controls, and say so in the docs. Examples: the tray's drop zone under the dialogue strip; the crashed engine staying in the workshop window.
- **Players' requests** that the original does not have are added as small modules (Christmas's `StageExtras`: the level select's BACK tag and Escape), marked "Not in the Flash game" in code and docs. They never change the original's scripts.
- **Approximations** the user accepted stay unless a play-test report says otherwise. Example: AS1's approximated wound areas. Play-test reports come before further reverse-engineering precision.
- **The pointer.** In an operation the game's cursor (the tool in hand) is the pointer, and the system's is hidden.
- **No pointer on a touch device.** On a touch device (a mobile port) there is no pointer: the finger is it. The game's cursor art (AS2's tool-in-hand cursor, the hand over buttons) is not drawn, nor the system's, and nothing that only follows a hovering pointer shows (hover looks; the torch steered by the pointer: there the tilt steers it). On the Flash stage (AS1, Christmas) the operation's cursor is not drawn, and a lifted finger rolls out of the button it was on, so no hover look stays.
- **A finger is not a mouse.** It lands with no hover before it, hides what it touches and lands less exactly: what a game moves with the pointer once a pass (the Flash games' cursor, whose `hit` the tools test on the press) is put where the finger landed before its press is handled, never a pass later (a pass of input lag), and what the game tests touches with (the cursor's `hit`) is made a fingertip's size. Both only on a touch device. The PC build always has a pointer; the touch builds are Android's ([port.md](port.md#building-and-running)).
- **Layouts by screen size, not by device kind.** A layout made for big screens (AS3's tool bar) is chosen by `platform::largeScreen()`: any PC window, or a touch screen whose shorter side is at least 600 dp; phones keep the original's layout. The choice is followed when the screen changes (a foldable, another display). Pointers stay a device question: drawn with a mouse, never on a touch device. Keys work wherever a keyboard is attached.

## 8. Rendering and motion

- **Smooth motion, no invented frames.**
  - The display runs at the screen's refresh rate.
  - What moves continuously is smoothed between passes: the game's own motion, and the art's tweens (the same drawing moving).
  - Authored changes step exactly at their pass: a mouth or pose drawing swapped, a frame-by-frame animation, letters, a jump.

  Check every motion change with `AS_FILM` and `port/tools/motion_check.py` / `motion_sweep.py`, in numbers, not only screenshots.
- **Art is rasterised at the size it is shown**, sharp at any window size, from worker threads when it can be asked for ahead.
- **No stalls.** A pass must not wait on rasterising. `AS_PROFILE=1` logs each pass and every piece of art made on the spot (`raster made at once: ...` in the debug trace); anything recurring there is a bug.
- **Few draws, no GL call while recording.** Small art is packed in shared pages and consecutive draws of a page go out as one (`platform/TextureAtlas`, `flushBatch`): a phone's driver pays for every draw. Game code's matrix calls go to the engine's CPU matrix stack (`GL.h`), never to GL, so recording never waits on another thread's GL work.
- **No pass longer than a pass.** The display runs on its own thread, a few milliseconds behind the logic (as long as passes take to compute): it never waits on a pass, but a pass that takes longer than its lead holds it. Texture texels go through `platform::setTexels` (the texture thread uploads them), never uploaded on the game's thread while the display draws. Check with `AS_DISPLAY_LOG` and `port/tools/display_pace.py`: no holds, no jumps, no slow display frames in real-time play ([engine.md](engine.md#the-loop-and-the-display-three-threads)).
- **Filters** are baked into the pieces' textures. Art under a large blur is rasterised at a lower resolution. A filtered clip that is also faded is rasterised whole and faded as one, as Flash drew it, so its overlapping pieces do not show through each other ([christmas.md](christmas.md)'s rendering notes).
- **An added colour is baked in; a fade over it is not.** A colour transform with a non-zero `add` (an "add" cannot be drawn with the fixed pipeline, e.g. a damage flash's added red) is rasterised with that tint baked into the texture — but its alpha (a plain fade, `mult` only, no `add`) is still applied at draw time, as any untinted art's is. Baking the fade too would rebake the whole texture on every step of it (a large tinted piece stalling for as long as the fade plays); keeping `add[3]` as the rare case that still needs a full bake.
- **A keyframe group's own pieces are never the previous pass's.** `KeyframeGroup` (DrawList.cpp) exists so a symbol's authored artwork (a mouth, a face, the cursor's tool icon) steps exactly at its pass while only the whole group's own placement (what the game moves it by) eases between passes — per the rule above. Between two passes, `renderFrame` must draw the group's pieces as the *just-computed* pass recorded them, with only their shared anchor eased from where the group was last; it must never hold the previous pass's pieces and ease them toward the new anchor instead — that shows the wrong keyframe (the old mouth shape, the old tool icon) for nearly the whole pass, snapping to the right one only for an instant before the next pass, which gets worse the higher the display's refresh rate (more of that wrong instant is actually rendered). This was the bug behind "keyframed motion is off at high fps", the cursor's tool icon warping when the mouse moves fast while switching tools, and a face's keyframes lagging during fast motion — all the same mechanism: anything that is both continuously moved by the game and keyframed inside.

## 9. Testing

**Test hygiene (never harm the player's game):**
- **Save folder.** Every automated run uses `AS_SAVE_DIR=<a scratch folder>` and the debug flag `-d` (without it `AS_*` variables are ignored and the real save is used). It also uses `AS_HIDDEN=1`.
- **Builds.** Test from `port/build-dev`. Rebuild `port/build` or `dist/` only to hand a build over, and only when the player's copy is not running.
- **Processes.** Never stop a game process you did not start. Check the exe's path first.

**Prove it by real play.**
- **Every mission end to end.** Every mission or patient is completed by a scripted play-through with the real tools (`AS_CONTROL` live driving, aimed by `AS_TRACE`), asserting that each stage advances. Christmas's are `port/tools/flash_playtest.py`'s `mission1`…`mission5`; AS2's are `port/tools/surgeon2_playtest.py`'s `missionN`, `fromN` and `onlyN` ([as2.md](as2.md#testing)).
- **The whole flow through the real menus.** One scenario plays the game as a player would, through its real menus and screens. Christmas's is `story`: new game, intro, story scene, START, a whole operation, the won scenes and banner, back to the level select with the grade saved.
- **Never a debug shortcut.** Never count something as working because a debug shortcut (skip stage, win now, the F1 mission menu) reached it.
- **After every change.** Run the whole suite after every change to the engine, a module or a package, and keep it green.
- **Keep the scenarios.** Scenarios are kept as regression tests, never deleted to make a run pass.

**Compare with the original** (`port/tools/ruffle_ref.py`, the original running in Ruffle; `xmas_ruffle_replay.py` replays a play-test's input on it):
- every screen, story scene, panel and HUD element, over time (animations, cursor, indicators, popups), not one still;
- a mission stage by stage.

**Prove refactors are invisible:**
- **Before and after.** Take before/after screenshots of the same input (`AS_CONTROL` boot frames, menus, operations) and a symbol sweep.
- **Same images.** Compare them in RGB. An alpha-only comparison once reported "identical" for everything.
- **Determinism first.** Seed the operation's randomness (`AS_SEED`). First check that two runs of the same build match: random scenes differ anyway, and their differences are not a result.

**Check the pipeline:**
- `extract_swf`'s round trip;
- `index_scripts.py --report` at 0 unported;
- every script parsing;
- generated data equal to what it replaced when a generator is rewritten (compare the data, not only the game).

**Report honestly.** Say what was verified and how, what failed, and what was not checked. A test tool's bug is a finding too.

## 10. Debugging tools

All need `-d`. `-d` by itself (`platform::traceEnabled()`) turns the `AS_TRACE` detail on with no env var needed, and everything it prints also goes to `debug.log` next to the save data (`prefPath()`) — the game is windowed, not console, so a manual playtest's stdout is not reachable otherwise; this is how a player's own `-d` playtest leaves something to read afterwards. `AS_TRACE=1` still works the same way and is what the test tools set.

| Tool | What it gives |
|---|---|
| `AS_TRACE=1` | Operations: injuries (created, stage, removed, with `id`, body level, glass box, hit pieces), critters, tools pressed (what they meet, health, blood), organs on the tray and dropped, hearts, patient lost and why, mission won.<br>Stage: `stage <label>`, `button <id> <event> on <path>`, `progress saved: ...`, `script: nothing answers <name>()`. |
| `AS_TRACE_VARS=a,b` | every set of those script variables |
| the wound log (`-d`), `AS_WATCH=prefix,...` | every attached injury clip (or those named so): its place, drawn bounds, opacity, frame and inner clips' frames (hidden ones marked), each time one changes ([engine.md](engine.md#running-the-scripts)) |
| `AS_TRACE_GOTO=1` (needs `AS_TRACE=1` too) | every `gotoAndStop`/`gotoAndPlay` a script makes: the part, its sprite, what it was given and the frame that resolved to (diagnoses a clip stuck playing instead of held, or re-rasterising every pass) |
| `AS_TRACE_SOUND=1` (needs `AS_TRACE=1` too) | every call on a `Sound` object: which one (its address, stable for the run), its linkage, and its channel's state before and after (`none`/`playing`/`stopped`) — a stuck, silent or wrongly-shared sound shows up in the trace instead of being re-derived by hand |
| `AS_TRACE_FRAME=1` (needs `AS_TRACE=1` too) | every frame script the scene runs: its sprite, the frame, its instance path — confirms whether a frame's script ran at all (as opposed to running but having no visible effect) |
| `AS_CONTROL=1` | live driving from stdin: `run`, `click`, `drag`, `key`, `down`/`move`/`up`, `shot`, `window` (resize), `quit`, each frame acknowledged with `@frame <n>` |
| `AS_SHOT`, `AS_CLICKS`, `AS_DRAG`, `AS_HOVER`, `AS_KEYS` | scheduled input and screenshots (`AS_SHOT_NATIVE=1`: at the window's pixels) |
| `AS_WINDOW=<w>x<h>`, `AS_ASPECT=<w>:<h>` | the window's size; the shape a game that follows the window's shape takes (AS3) |
| `AS_PROFILE=1` | per-pass times, art made on the spot |
| `AS_FILM` | where every draw lands at each display step (motion checks) |
| `AS_DISPLAY_LOG=<file>` | each display frame: when, which frame, how far eased in, draw and swap times (`port/tools/display_pace.py`: holds, jumps, missed refreshes) |
| `AS_ONE_THREAD=1` | the frames shown by the game's thread between passes (Android's way), to compare with the display thread |
| `AS_RASTER_ART=1` | Flash art rasterised to textures as before the GPU meshes, to compare |
| `AS_MSAA=<n>` | the window's multisampling (default 4; 0: none) |
| `AS_SEED=<n>` | repeatable randomness |
| `AS_VECTOR_SYMBOL`, `_FRAME`, `_AT`, `_SCALE`, `_TREE` | one symbol on an empty stage |
| F1 menu | screens, missions, skip/win/heal/time/kill, god mode, smooth motion, unlock all |

## 11. Documentation and handing over

- **Docs.** `docs/` is kept current in the same task as each change:
  - [engine.md](engine.md): the engine and package format;
  - one page per game ([christmas.md](christmas.md), [as2.md](as2.md));
  - [port.md](port.md): layout, building, dist;
  - this page: the rules;
  - [README.md](README.md): the index.

  Docs describe what exists and why, not a changelog.
- **Hand over a build.** When a build is handed over, rebuild `dist/<game>/` from a clean `assets/` folder, start it once without debug flags, and say what changed and what to look at.
- **Ask, don't assume.** A rule the user sets is written here, and a design decision that goes beyond an approved plan is stated plainly so the user can object.

## 12. Working practice

- **Generated files are regenerated, never edited by hand:**
  - `games/<game>/vector`, `audio`, `library.json` (`extract_swf`);
  - `scripts/index.json` (`index_scripts.py`);
  - `data/gamedata.json` (the game's data tool).
- **Builds.** Build while no test is running from the same build folder (the exe is locked).
- **Edit scripts in files.** In this shell, escapes inside heredocs get mangled (`\n`, `\\`, `\U`). Write edit scripts to files with the editor and run those, or use the editor directly.
- **Edits with a pattern** must fail loudly when the pattern is not found, never half-apply.

## 13. Porting a Flash game, step by step

1. **Get the original.** Put the SWF (and anything it loads from a server) under `re/flash/<game>/`.
2. **Extract it.** Run `extract_swf <swf> port/games/<game>`, and add the build step. Put loaded files in `data/`.
3. **Index it.** Run `index_scripts.py <game> --swf <swf> --report`.
   - Write `data/modules.json`: the online parts to `removed`, the clips that are real game logic to their modules. Get to 0 unported.
   - Run `--diff` against the games already ported.
4. **Set up the stage.** Write the game's set-up: the save file and key renames (keep any earlier port's save readable), the transition variable, the module registrations, the bindings of `_root` variables the modules share.
5. **Write the modules** the report asks for, reusing shared code. Any engine feature they need is added to the engine (§1).
6. **Build the play-tests before calling anything done:**
   - the trace lines for the game's operation;
   - a live driver that completes every patient with the real tools;
   - a scenario through the real menus;
   - Ruffle replays.
7. **Verify** (§9), **document** (§11), hand over `dist/<game>/`.
