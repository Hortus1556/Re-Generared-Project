# Windows port — layout and setup

Native C++ games on SDL3 + OpenGL + miniaudio, built with llvm-mingw (AS2 also for Android, below). They share one engine, which is to run every Amateur Surgeon ([plan.md](plan.md); rules in [rules.md](rules.md)):
- **Christmas** (`AmateurSurgeonXmas.exe`) is rebuilt from its Flash original. The original's own scripts run on the engine's stage, with its operation as a native module ([christmas.md](christmas.md), [engine.md](engine.md)).
- **Amateur Surgeon 1** (`AmateurSurgeon.exe`) is being rebuilt from its Flash original: the whole game, operation included, runs by its own scripts on the stage ([as1.md](as1.md)). Its earlier port from the iPad app (a game layer mirroring the iOS code) is archived in `port/attic/as1-ipad/`.
- **Amateur Surgeon 2 HD** (`AmateurSurgeon2.exe`) is the port of its iPad app (`src/as2/`, the iOS classes mirrored, its screens on the engine's UIKit layer), with parts of its Flash original drawn as vector art ([as2.md](as2.md)).

Background analysis: [amateur-surgeon-1-ipad.md](amateur-surgeon-1-ipad.md), [amateur-surgeon-christmas.md](amateur-surgeon-christmas.md). Online services (OpenFeint, Facebook, Twitter, the HS high-score server, Adult Swim's score submission) are removed, not ported.

Sections about AS1's iPad port (its screens, wounds, tools, the iOS framework port in `src/engine/`, `port/assets/`) describe the archived port, kept for reference.

**Published.** The buildable source (this engine, every game's own code, the build system, the tool scripts — never game content) is mirrored publicly at [Re-Generared-Project](https://github.com/Hortus1556/Re-Generared-Project); the generic engine alone (no game-specific code) is also published on its own at [Bleed-Engine](https://github.com/Hortus1556/Bleed-Engine). `BuildAllGames.exe` pulls from the former when run outside this checkout (see "Fetching sources and a full build" below).

## Assets

Create or refresh them with:

```
python port/tools/extract_ipa.py "IPAs/A.Surgeon_v1.0.3_os32.ipa" port/assets
```

The script copies only game data. It skips the iOS executable, the nibs, `FBConnect.bundle`, OpenFeint's `OF*` images and `.inl` files, and the developers' notes (`Readme.txt`, `changeLog.txt`, `setup.txt`). Root-level files of the app bundle are sorted by type:

| Folder | Extensions | Contents |
|---|---|---|
| `images/` | png, jpg | Sprites, atlases (`ipad_*`), backgrounds. PNGs are standard straight-alpha RGBA (see below). |
| `audio/` | mp3, wav | Music and sound effects (`Sound_N`) |
| `video/` | mp4, m4v | Splash and story-intro movies |
| `anim/` | txt, anu | Animation, frame-offset, and path data, plus `PNGpackinglist.txt` (atlas map); `.anu` are Christmas's MotionWelder animations |
| `dialogue/` | xml | Story dialogue scripts and their per-level sequence |
| `models/` | POD | PowerVR 3D models (poison) |
| `lang/` | txt | String tables; keeps the bundle's own `en/` and `bala/` subfolders |

The bundle's PNGs are Apple CgBI "crushed" files (BGRA, premultiplied alpha, raw deflate) that ordinary tools cannot open. The script writes them as standard PNGs instead, with exactly the pixels the engine's decoder (stb_image) produced from the CgBI files: checked bit for bit over all 1467. The engine still loads CgBI files from an older extraction.

The game code refers to files by their original flat bundle name (for example `Sound_12.mp3`). The engine therefore resolves a bundle name to `assets/<folder>/<name>` using the same extension table as `CATEGORY` in `extract_ipa.py`, and the two must stay in sync. The script stops with an error if it meets an extension that isn't in the table. A flat name its type's folder does not hold is then looked for at the assets' root: a Flash package's own `library.json` sits there (Christmas's), while AS2's catalogue is `data/library.json` (`.json` files go to `data/`).

`ipad_sidestreet.txt` (Bleed's street scene) places the three pieces of its lamp light where `ipad_sidestreet.png` no longer has them (one region is empty, the others about 15 pixels off), so the light came out as a box over the wall; `ResourceSpritexData` corrects them to where the image has them (and trims the one row two of them shared).

`PNGpackinglist.txt` gives the pause board's two help notes 255 pixels wide, into their neighbours on `ipad_res_pause.png`; the engine corrects them to the notes' 225 (the size of the bundle's standalone copies). The pause buttons also draw their notes whole, where the original cut each to its button's touch size (straight cut edges, and a jump when the board finished swinging in).

To make re-runs safe, the script writes a `.extracted_from` marker. It only ever deletes an existing destination that contains that marker, and refuses any other non-empty folder.

Christmas's assets are not extracted from its IPA. Its art and sounds are the Flash movie's (`re/flash/xmas/`), extracted into the game package `port/games/christmas/` (SVG shapes, JSON symbols, MP3 sounds) by the `extract_swf` tool when the game is built; the SWF is not shipped. Its story scenes are `data/dialogue.xml`, and its game data is generated by `port/tools/flash_data.py` ([christmas.md](christmas.md)).

## Fetching sources and a full build

`re/flash/` and `IPAs/` must hold the originals before any of this works. `port/tools/sources_manifest.json` lists every one of them by path and sha256; `port/tools/fetch_sources.py [--game as1|xmas|as2|as3|all]` checks each against the manifest and, for the ones with a known source, downloads and re-verifies it:

- **Auto-fetchable from archive.org, verified by hash**: AS1's `game.swf` and `dialogue.xml` (item `AmateurSurgeonFlash`, collection `softwarelibrary_flash`); the Christmas IPA (`com.turner.amateursurgeonxmas-ios3.0-clutch-2.0.4`); the AS3 IPAs, both 1.02 (`Amateur_Surgeon_3_1.02_ios_6.0`) and 1.45 (`Surgeon_3_1.45_ios_6.0`, already credited in [amateur-surgeon-3.md](amateur-surgeon-3.md)).
- **Auto-fetchable from Flashpoint's own Legacy htdocs mirror, verified by hash**: Christmas's SWF and AS2's six (`shell.swf`, `shell_preloader.swf`, `sounds.swf`, `game.swf`, `assets.swf`, `cut_scene.swf`) — `https://infinity.flashpointarchive.org/Flashpoint/Legacy/htdocs/<host>/<path>`, the host+path taken straight from each entry's own `re/flash/...` manifest path. (An earlier pass concluded these had no automated source at all — that was simply an undertested dead end, not tried for each file or with the path's space properly percent-encoded; retried properly, every one matches byte-for-byte.)
- **No automated source found** (archive.org's `ipaarchive` collection, general search, and a web search for the exact filenames, all checked again): the AS1 iPad IPA (`A.Surgeon_v1.0.3_os32.ipa` — only v1.0.0 is archived) and the AS2 HD IPA (`Amateur Surgeon 2 HD v1.2 iPad os32most_uniQue.ipa` — only v2.3 and other versions are). These exist only as the copies already in `IPAs/`; there is nowhere found yet to refetch them from if lost.

`fetch_sources.py` never overwrites a file that's present but doesn't match the manifest (only ever fills in something that's missing), and never claims success for a file it couldn't get.

**Running from outside this checkout.** `fetch_sources.py` (and everything built on it: `build_all.py`, `BuildAllGames.exe`) prefers a checkout it's already running from (two levels under `port/tools/`, no network touched) — but if it isn't inside one (the exe copied somewhere else, or run from a bare download), it clones [Re-Generared-Project](https://github.com/Hortus1556/Re-Generared-Project) — the full buildable source (this engine, every game's own code, the build system, these tool scripts; never the copyrighted assets) — into a `Re-Generated-Project` folder next to wherever it's running, and `git pull`s it on every later run so it's never stale (best-effort: offline or a conflict just means building with whatever's already there, not a hard failure). Needs `git` on `PATH`. This is what makes `BuildAllGames.exe` usable dropped anywhere, not only inside this exact checkout — though it still can't conjure the sources with no automated fetch (above) from nothing; those must already exist, or be supplied, in the resulting tree's `re/` and `IPAs/`.

`python port/tools/build_all.py [--game as1|xmas|as2|as3|all] [--platform windows|linux|android] [--no-fetch]` runs `fetch_sources.py`, then extracts AS2's and AS3's IPA-based packages (`extract_ipa.py`, plus `brain_dial.py` and `as2_data.py` for AS2 — these two aren't wired into CMake the way the Flash-sourced packages are; this step is the same regardless of target platform), then builds for the chosen platform. `music restored/` (the user's own restored audio, read straight from the workspace root by `CMakeLists.txt`) travels with the tool as `port/tools/music-restored.zip`: `build_all.py` unzips it in place if `music restored/` is missing, and never touches it if it's already there.

**Windows** (the default): configures a dedicated `port/build-release` (never `port/build-dev`, so it can't collide with a test build in progress) and runs each requested game's `_dist` target, landing in the usual `dist/surgeon1`, `dist/surgeonxmas`, `dist/surgeon2`, `dist/surgeon3`.

**Linux** (`--platform linux`): needs WSL with an `Ubuntu` distro (tested there; `wsl --install` if it isn't set up). Runs `port/tools/linux/build.sh` inside it, which:
1. `setup_sdl3.sh` builds SDL3 for Linux from the same source as Windows/Android (`tools/sdl3-src/`), once — idempotent, skips straight through on later runs. No `sudo` needed: the handful of `-dev` packages missing from a bare WSL image (X11, EGL, GL, ALSA, PulseAudio headers — nothing the engine doesn't already need on Windows) are fetched with `apt-get download` (unlike `apt install`, needs no root) and extracted with `dpkg-deb -x` into `~/linuxdeps/root`, never touching the system's own paths; the runtime `.so`s themselves (`libGL.so.1`, `libX11.so.6`, ...) are already present via WSLg. Wayland, Vulkan, pipewire and the camera backend are left off (`-DSDL_WAYLAND=OFF` etc.): the available `wayland-protocols` package is older than this SDL3 expects, and the engine doesn't use the other three anyway — X11 (via WSLg, or any real X server) is enough.
2. Configures and builds `port/build-linux` with `CMAKE_PREFIX_PATH` pointing at that SDL3, same `*_dist` targets as Windows. `CMakeLists.txt` appends `-linux` to the dist folder name for a non-Windows, non-Android build (`add_game`), so this can never land in the same `dist/surgeon1` a Windows build already populated — output is `dist/surgeon1-linux`, `dist/surgeonxmas-linux`, etc.

   The engine's platform layer turned out to need almost no Linux-specific code: `WinShell.cpp` and `CrashLog.cpp` already had a working generic fallback for non-Windows (no Saved Games folder lookup — falls back through `SDL_GetPrefPath`/`./`; no crash handler), and nothing else in `port/src/platform` or `src/engine/{cocos,ui}` touches a Windows-only API. The one real gap: **`MovieDecoder.cpp`** (AAC music, movie playback) was Windows Media Foundation only, with an Android branch (NDK codecs); it now has a third, Linux branch that reports "absent" rather than decoding anything (`decodeAudioFile`/`decodeAudioFileStreamed`/`MovieDecoder` all return false/nullptr) — AS1 and Christmas use neither (their sound is MP3/WAV through miniaudio, unaffected), so they're unaffected; **AS2's `.m4a` music and AS3's movies won't play on Linux yet.** A real implementation would plug into that same `#else` branch, e.g. with ffmpeg's libavcodec (already a tool dependency here).

   Verified by actually running it (not just compiling): `AmateurSurgeonXmas` built this way, copied to WSL's own filesystem (cross-filesystem `/mnt/c` access through 9p is correctness-fine but slow — tens of seconds just to read the package's small files, vs. tens of milliseconds natively) and run headless (`AS_HIDDEN=1 AS_SHOT=...`) through WSLg's X11, produced correct, pixel-real screenshots of the title screen — sounds attached, the save file written, the title music started. AS2/AS3 haven't been built or run for Linux yet (only AS1/Christmas, whose dependencies are the ones checked above); `cocos`/`ui` have no Windows-specific code either, so they likely build, but the AAC/movie gap would need addressing to actually play.

**Android** (`--platform android`): runs `port/tools/android/build_apk.py --game <as1|christmas|as2|as3>` per requested game (translating this tool's `xmas` to that script's `christmas`) — the same tool and output (`dist/<name>-android/`) [already documented below](#building-and-running); needs the Android SDK/NDK and a JDK, same as running it by hand.

**No external Python needed**, for the parts that don't inherently require a separate process: `extract_ipa.py`, `brain_dial.py` and `as2_data.py` are imported and called directly rather than run as a subprocess of `python`, so building AS1/Christmas for Windows or Linux needs no system-wide Python install at all, even frozen into `BuildAllGames.exe` below. Two things still do, on purpose, kept as separate processes rather than bundled in: `build_apk.py`'s Android toolchain orchestration (`--platform android`), and `as2_data.py`'s own `emulate()`, which shells out to `re/scripts/emucalls.py` (a real ARM emulator over the AS2 binary, via `unicorn`) — both resolve a real interpreter with `fetch_sources.python_exe()` (searches `PATH` for `python`/`py` when this process is itself frozen, since `sys.executable` would otherwise be the frozen exe, not a Python interpreter).

**`port/tools/BuildAllGames.exe`** is a GUI for the same thing: radio buttons for the platform, checkboxes for which games to build and whether to fetch sources first, a Build button, and a live log (including, now, the bundled extraction scripts' own `print()` output, forwarded via a small `contextlib.redirect_stdout` writer — skipped when the caller's `log` is plain `print`, i.e. the CLI, where that would otherwise recurse). It's `build_gui.py` (tkinter) frozen with PyInstaller; both it and `build_all.py`'s CLI call the same `run_build()` function, so there's one implementation, not two. It can be dropped and run anywhere (see "Running from outside this checkout" above) — inside this checkout's own `port/tools/`, it builds that checkout directly with no network access; moved somewhere else, it bootstraps and then keeps updated its own clone next to itself. Rebuild it after changing `build_gui.py`, `build_all.py`, `fetch_sources.py`, or the bundled extraction scripts:

```
python -m PyInstaller --onefile --noconsole --name BuildAllGames --distpath . --workpath ../build-release/pyinstaller-work --specpath ../build-release build_gui.py
```

(run from `port/tools/`; needs `pyinstaller`, `numpy` and `Pillow` installed for whichever Python is on `PATH` — the same Python then has everything `extract_ipa.py`/`brain_dial.py` need, which PyInstaller bundles in).

## Building and running

```
cmake -S port -B port/build -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/llvm-mingw.cmake -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build port/build
port/build/AmateurSurgeon.exe
port/build/AmateurSurgeonXmas.exe
port/build/AmateurSurgeon2.exe
```

Each exe is statically linked apart from `SDL3.dll`, which the build copies next to it. It looks for `assets/` next to itself, then for its game's folder in the source tree (`../assets/` or `../games/christmas/`), so `port/build/` finds `port/assets/` and `port/games/christmas/`. Each carries its game's icon and version name ("Amateur Surgeon", "Amateur Surgeon Christmas": what Windows shows for the running game).

**Handing it out:** `cmake --build port/build --target dist` (or `AmateurSurgeon_dist`) fills `dist/surgeon1/` with the exe (debug info stripped), `SDL3.dll` and the `assets` folder (AS1's package `games/as1`: [as1.md](as1.md)); that folder is the whole game. Each dist target clears the `assets` folder before copying, so no file the package dropped (a sound replaced by one of another format) stays behind. `AmateurSurgeonXmas_dist` does the same for Christmas in `dist/surgeonxmas/`, its package `games/christmas` copied as `assets`, `AmateurSurgeon2_dist` for AS2 in `dist/surgeon2/` (its package `games/as2`), and `AmateurSurgeon3_dist` for AS3 in `dist/surgeon3/` (its package `games/as3`).

**Android (AS1, Christmas, AS2, AS3).** `python port/tools/android/build_apk.py [--game as1|christmas|as2|as3] [--abi arm64-v8a,x86_64]` builds `dist/surgeon1-android/AmateurSurgeon.apk` (AS1, about 20 MB), `dist/surgeonxmas-android/AmateurSurgeonXmas.apk` (Christmas, about 20 MB), `dist/surgeon2-android/AmateurSurgeon2.apk` (AS2, the default) or `dist/surgeon3-android/AmateurSurgeon3.apk` (AS3, about 250 MB) with the Android SDK's own tools, no Gradle: the game per ABI with the NDK's CMake toolchain (`port/build-android-<abi>` for AS2, `port/build-android-as3-<abi>`, `-as1-<abi>`, `-xmas-<abi>` for the others; CMake's `ANDROID_GAME` picks the game built as `libmain.so`, the Flash games with the stage, `src/surgeon`; `libSDL3.so` from `tools/sdl3-src`), SDL's Java glue compiled and dexed, the manifest and resources linked by aapt2 (the game's name and app id, `org.bleedengine.amateursurgeon`, `amateursurgeonxmas`, `amateursurgeon2`, `amateursurgeon3`, and its launcher icon made from its Windows icon; `GAMES` in the script), the package `games/<game>` as the APK's `assets/game/` (already-compressed files stored: pictures, the music, the movies, AS3's `.ccz` sheets), aligned for 16 KB pages and signed with the debug key (`~/.android/debug.keystore`, made if missing). It needs the SDK (`ANDROID_HOME`, else `%LOCALAPPDATA%\Android\Sdk`) with an NDK, build tools and a platform, and a JDK (`JAVA_HOME`); it takes the newest of each. Minimum Android 9 (API 28). How the shared code runs there: `--test` builds a test copy beside the real one (`<id>.test`, "(test)" in its name, `-test.apk`): its own save, and debuggable, so `adb shell run-as <id>.test` reads and writes `files/state.json`.
- **Graphics:** OpenGL ES 1.1, the original's own pipeline (`platform/GL.h` maps the desktop names; texels go up as RGBA, `platform::toTexelOrder`). The activity asks for landscape (`sensorLandscape`) and takes size changes itself (`configChanges` with `screenSize|smallestScreenSize|screenLayout`: a foldable folded or unfolded, a window resized in multi-window), which SDL passes on as a new window size; on a near-square screen (an unfolded foldable) Android letterboxes it to landscape. AS2 letterboxes its fixed screen in what it gets; AS3 takes the window's shape as its screen at its next screen change ([as3.md](as3.md#the-screens-shape-the-ports)), so the unfolded Pixel Fold's 4:3 window is filled.
- **Files:** the package is read from the APK by SDL's relative paths (`assets::` root `game/`); the save goes to the app's own folder (`SDL_GetPrefPath`).
- **Sound:** AAC through the NDK's media codecs (`platform/MovieDecoder.cpp`), gapless trim kept. The codec answers one 1024-sample frame at a time, so a whole track is slow to decode (the intro movie's 95 s soundtrack took 9 s, a menu's music about 1 s): music in AAC and movies' soundtracks are played as they decode (`platform::decodeAudioFileStreamed`, the engine's streamed source in `MediaPlayer.cpp`: a worker thread fills the samples, the mixer plays what is there; the intro now starts in 0.3 s). The codec's buffers are filled at once and waited on only briefly.
- **Movies:** the video track decoded by the NDK's codec into its buffers, each frame's YUV 4:2:0 read by the layout its output format gives (`image-data`, a MediaImage2: planar, semi-planar or "flexible") and turned into BGRA (BT.601, fixed point), uploaded as RGBA (`toTexelOrder`).
- **Fonts:** the system's (`platform::systemFont`: Roboto for Helvetica, a handwritten face for Marker Felt).
- **Input:** touch is the pointer, and none is drawn ([rules.md](rules.md) §7); tilt and shake come from the accelerometer; the back button is Escape (AS2's and AS3's pause; the Flash games' scripts take no Escape in an operation, on the PC either, so there it does nothing but Christmas's level select's BACK).
- **The Flash games by touch** (AS1, Christmas): the operation's cursor (the tool in hand, the stage's pointer clip) is not drawn (`ArtNode::draw`), and a finger lifted is the pointer leaving: the button it was over gets its `rollOut` and no hover look stays (`StageScreen::touchUp`; the pause screen's items, the level select's BACK). A finger landing somewhere new has no hover before it: the scripts move their cursor to the mouse once a pass (`cursor._x = _xmouse` in the operation's `onEnterFrame`) and test what a tool touches with the cursor's `hit` on the press (the tongs' grab, `StartTongs`), which was where the last touch had ended; so the stage puts its pointer clip where the finger landed before it handles the press (`StageScreen::touchDown`), as the scripts would have by the next pass (the press once waited that pass instead: input lag). That `hit` is a 9.5-pixel square, exact under a mouse but hidden and imprecise under a finger: on a touch device it is three times as wide and high (`StageScreen::pointerHit`). Their packages are the ones the Windows build makes (`port/games/as1`, `games/christmas`, with the restored sounds): build that first. Verified on the emulator (Pixel 10 Pro Fold, unfolded, ANGLE as below), 2026-10-24: AS1's title, a new game's intro and story skipped, patient 1's operation (the cutter picked from its card, the incision cut by a swipe, a rib of the rib cage grabbed with the tongs and dropped in its place), its pause by the button (a sound toggle, Resume), the app sent home and back twice; Christmas's title, intro, mission 1's operation with a tool picked. - **The display thread** runs on Android too, its contexts without a surface ([engine.md](engine.md#the-loop-and-the-display-three-threads)): on the emulator a pass went from transitions of 100–230 ms (art uploaded on the game's thread) to a median of 2 ms.
- **Debug on a device:** a file `debug_env.txt` in the app's save folder, `NAME=VALUE` lines (`{save}` in a value is that folder), turns debug mode on with those variables (`AS_PROFILE=1`, `AS_DISPLAY_LOG={save}disp.txt`, `AS_TRACE=1`), and stdout and stderr go to `stdout.txt` and `stderr.txt` beside it. ## Port architecture

The port mirrors the original classes one to one, so each decompiled method has exactly one C++ counterpart. Translation conventions:

- **Ownership:** `core/Object.h` provides intrusive retain/release (`Object`) and `Array<T>` (an `NSMutableArray` that retains its elements). `[x retain]`/`[x release]` become `retainRef(x)`/`releaseRef(x)`. Both accept null, because messaging nil was a no-op; any other call on a possibly-nil object needs an explicit null check.
- **Names:** a selector's keyword parts are concatenated, so `initWithPath:Row:Col:Data:` becomes `initWithPathRowColData`. `alloc`+`init…` becomes a static factory returning a +1 reference, or `nullptr` where the original returned nil.
- **Ivars:** stay public data members with their original names, since game classes poked each other's ivars directly.

**Layers:**

| Layer | Path | Responsibility |
|---|---|---|
| Platform | `src/platform/` | SDL3 window and GL context; recorded drawing replayed at native resolution with smooth motion (`DrawList`); mouse as a single touch; asset lookup; save path; the device's accelerometer where there is one (`deviceTilt`: the tilt in the screen's axes, allowing for how the display is turned; none on a PC, the trace's `accelerometer <name|none>`; `deviceAcceleration`, its whole reading in gravities, for shakes); the arrow keys to the game (`TouchSink::arrowKey`, pressed and let go: a tilt held by hand on a PC); the main loop (`GameMain.h`) and the engine's splash (`Splash.cpp`, [engine.md](engine.md#the-splash-powered-by-bleed-engine)) |
| Engine | `src/engine/` | Port of the "A3I" framework: `ResourceManager`/`ResourceTexture`/`ResourcePackedImageData`, `AdvancedImage`, `FrameData`, … |
| Flash | `src/flash/` | SWF parser, game packages (SVG, JSON, audio), the vector rasteriser and its filters |
| Stage | `src/surgeon/` | A game run by its own translated scripts: `StageScreen`, `Scene`, `Script`, `FlashClasses`, `ArtNode`, sounds, debug menu ([engine.md](engine.md)) |
| Game | `src/as1/` (AS1's set-up and debug probe); `src/christmas/` (Christmas's set-up, additions, operation) | What the scripts do not do: Christmas's operation; AS1's debug trace |

### Three games, one engine

The platform, engine and Flash layers serve every game. They are Bleed Engine, built once as the static library `BleedEngine`; each game is an executable made of its own layers on top (`add_game` in `port/CMakeLists.txt`; Christmas adds `src/surgeon`). The engine is the same for every game: what a game needs is added to it generally, and no game script is hard-coded in it ([rules.md](rules.md) §1).

- **What differs per game** is `platform::GameInfo`, given to `platform::init`: the title (window, error boxes, Saved Games folder), the screen size (AS1: the iPad's 1024×768; Christmas: its Flash stage, 600×460), the game's assets folder in the source tree, and its old save folder name. The shared layers read the screen size from `platform::screenWidth()/screenHeight()`: the projection, the letterbox, screenshots, movies, and the smooth-motion teleport distance (160 pixels on the iPad's 1024-wide screen, the same share of a smaller one).
- **Each game follows its source.**
  - AS1 runs its Flash original's own scripts on the stage, its operation too ([as1.md](as1.md)). Its archived iPad port followed its iOS binary (`re/as1/ann/`), with classes of the original names (`GameCanvas`, `GamePanel`, …).
  - Christmas runs its Flash original's own scripts on the stage, its operation ported from them ([christmas.md](christmas.md)).
  - AS2 (`src/as2/`) follows its iOS binary (`re/as2/ann/`) class by class, its screens on the engine's UIKit layer, with the Flash AS2's pieces drawn by `VectorArt` ([as2.md](as2.md)).
- `main` is one line per game: `platform::runGame<...>(argc, argv, info)` (`src/platform/GameMain.h`), so the pass timing and smooth-motion loop exist once. A canvas class with a static `preload()` (Christmas: `VectorArt::preload` of its package) has it called before the engine's splash, so the game's content is read on worker threads while the splash shows: a new build's thousands of package files, scanned by the antivirus on their first read, otherwise held a black screen for seconds after the splash.

**Facts from the original that the engine relies on:**

- **Screen:** iPad landscape. Every panel sets `glViewport(0,0,1024,768)` and `glOrtho(0,1024,768,0,-1,1)` (y down). OpenGL ES 1.1 fixed function maps directly to desktop GL compatibility.
- **Main loop:** `GameCanvas cycle` runs on its own thread. Each pass swaps in a pending panel, steps panel loading, replays queued touch began/moved/ended as `mouseTouchDown/Drag/Up`, draws (`redisplay` = `cycle` + `clearContext` + `draw`), then sleeps 0.05 s. Game logic is frame-based, so the port runs one pass per 50 ms.
- **Screen routing (`DispatchEventIntoView`):** 1 Splash, 2 MainMenu, 3 PatientSelection, 6 LoseGame, 7 WinSplash, 10–39 Operation01–30, 50 StoryBoard; anything else goes to PatientSelection.
- **Sharper images:** an `images-svg/<name>.svg` (vector source, rasterised for the display's resolution) or an `images-hd/<name>` (the same picture at exactly twice the size) is loaded in place of `<name>` and reported at the original's sizes, so frames and texture coordinates are unchanged. Only the archived iOS Christmas port used them; AS1 has none.
- **Textures:** power-of-two, image in the top-left corner, straight (un-premultiplied) alpha, `GL_LINEAR`. Sprites draw with `glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)` as a 4-vertex triangle strip. Frame sizes come from the image size; texture coordinates divide by the power-of-two size. The original halved any image whose texture exceeded 1024 while still dividing by the halved size, and the art compensates (the lose screen's face and eyelids are drawn at ratio 2). The port uploads such images at full resolution and reports the halved size to `AdvancedImage`, so the coordinates land on the same image points with all the detail (only images beyond the driver's `GL_MAX_TEXTURE_SIZE` are still halved).
- **Data tables:** static tables are generated into `src/game/GameData.{h,cpp}` by `re/scripts/gen_tables.py as1` (`xmas` wrote the archived iOS Christmas port's). Examples are `fontMetric` (3 fonts × 95 glyphs × {x, y, width}; Christmas has a fourth, `font_xmas`) and `patientMaxScore` (Christmas: 35, its five patients last). To add a table, add a line to the game's table list in that script and re-run it.
- **Resource names:** iPad assets carry an `ipad_` prefix (`DeviceConfiguration stringWithResPrefix:`). The port uses the prefixed names directly and drops the iPhone branches.
- **Time:** almost everything counts game passes, but `Spritex` animation, story-board countdowns and the hourglass run on a clock. The port gives them `platform::passTime()`, the time the current pass was due, so they advance exactly one pass (50 ms) per pass and interpolate evenly (real time would sample them at uneven moments, as passes start whenever the display's refresh lets them). Only movies run on real time. Story scene backgrounds (`Spritex::setMinFrameMs(100)`) keep each frame at least two passes: their lamps' frames say "next update", and the iPad could not run updates at a full 20 a second, so they flickered slower than here (a port choice from play-testing).
- **Audio:** sound effects are keyed by file name plus a sub-key, volumes run 0–100, a replay count of -1 loops forever, and music always loops.

**Removed with the online services:** OpenFeint (dashboard button, achievements, challenges, leaderboards), Facebook/Twitter sharing, the "HS" high-score server, and the main menu's "More Games" App Store link. Vibration is a no-op on PC.

**Rendering and frame rate (`src/platform/DrawList`, `Platform`):** game code still draws as on the iPad (1024×768 `glOrtho`, matrix stack, `AdvancedImage`, `Morph` meshes), but nothing is rasterised while a pass runs. Each draw is recorded with what it was drawn under (the game's matrices, kept by the engine on the CPU, `GL.h`: as a 2D transform to screen pixels), and an image draw with its own parameters in `AdvancedImage`'s form: position and angle (what the game animates) and frame offset, pivots, corners and texture coordinates (the drawn content); `platform::Sprite`. The game's `glClearColor` + `glClear` became `platform::clearScreen`, which starts the frame over. Each logic pass ends with `endFrame`, which commits the frame. A display thread shows the committed frames once per display refresh (vsync; capped at 240 Hz without it), on its own clock: each frame from a few milliseconds after its pass was due (as long as passes take), eased in from the one before as `t` goes from 0 to 1 over the pass, so every pass takes exactly the same time on screen however long its logic took, and a pass never holds the display (the threads, the texture uploads, the shared pages and batched draws, and how to check the display's pace: [engine.md](engine.md#the-loop-and-the-display-three-threads)). Where there can be no display thread (an Android driver without surfaceless contexts, `AS_ONE_THREAD`) the main loop shows the frames itself between passes (`show(t)`):

- The display replays into the window at native resolution, in the largest centred 4:3 area, so sprites, text and rotations are rasterised at full window resolution instead of being stretched from 1024×768.
- **Smooth motion without invented frames** (always on in normal play; the debug menu can turn it off): the display runs one pass behind the logic. Between two passes it shows the previous frame's content (which animation cell, which story keyframe, which letters: everything authored steps exactly at its pass, as in the original) while what the game changes from pass to pass moves evenly towards the current frame's values: positions, angles (turning around the right pivot, so a swing follows its arc), the parent transform as translation, turn and scale (zoom, slides), sprite scale, colour and fade. What a pass adds appears, and what it removes vanishes, when the display reaches that pass, in step with everything that moves (a card's text shows when the card has settled). Changes too big to be motion stay cuts: a colour or fade changing by more than half in one pass (a blink), a turn of more than 90 degrees (a flip).
- **Keyframed art** (`Spritex`: story characters and scenes, the win animation) is drawn inside a `platform::KeyframeGroup`: its pieces change exactly at their keyframes, and only the transform the whole art is drawn under moves smoothly. Sliding pieces between keyframes is what made bandages and mouths look as if they broke apart.
- **Pairing** a draw with its previous-frame self: draws are attributed to the object that made them, the image object plus the enclosing `platform::DrawOwner` (`Layer` wraps every wound and effect, `ScoreTimer` every pop-up word, `TextDrawer` every string). Both are identified by `Object::serial()`, which, unlike an address, is never reused. Within that, a draw of the same image region is taken: the one in the same place in drawing order when the owner draws as many of them as before (a string's letters, which can move further per pass than the gap between two equal letters), else the nearest unpaired one (particles that came or went); else, if the owner draws that texture only once in both frames, that draw (an animation that stepped to another cell); else, if the owner draws only once in both frames, that draw whatever its picture (an animation that stepped to another picture: AS2 animates by swapping whole textures, so a tick flying with its wings beating or a splatter blob changing as it flies kept stepping at the pass rate). A picture swap shows the old picture, at its own size, gliding until the pass; only then the new one: no blend, no morph. A draw whose centre moved further than 160 pixels and further than its own size is a teleport and is not interpolated.
- **Vector art** (the Flash games' pieces, `VectorArt`) tells the display each piece's place in the art, the bounds of its texture, the clip holding it and its drawing (`platform::artPiece`): between passes it moves by those rather than by its corners, so a piece keeps gliding when another texture shows the same drawing (rasterised anew at another size), and a piece that changes drawing, or goes, rides with its clip until its pass instead of standing still while the pieces around it move on. A placement that flips (mirrored on the way) or turns over (more than 90 degrees) is a cut, as a sprite's flip: held until its pass, then stepped (eased, mission 3's kidney swapped to the other side swung across the middle of its pass). A mask (`stencilMode`) goes into the stencil by its texels' own alpha, not its fade: a mask on a clip fading in is its whole shape from the start (tested with the fade, every mask was empty below 50%, and what it showed missing for half a crossfade).
- **Crops:** a draw whose image region grew or shrank from one corner (a pop-up word written out left to right, the loading bar, a body rising out of a cut) has its texture coordinates interpolated along with its corners, so the image is revealed smoothly.
- **Touch targets lead:** the markers the player follows with the finger (the corkscrew's, the vacuum gauge's) must not lag behind the logic, which tests touches against where they are now. Before drawing one, the effect tells the presentation its exact next step by the game's own rule (`platform::nextStep`: the gauge's 6 pixels, reversing at its ends; the corkscrew's 10 degrees), and the marker is shown from where the logic has it on towards that step: never behind, never overshooting where it turns back.
- **The pointer's art** (`platform::PointerArt`: AS2's and AS3's Flash cursor, AS1's and Christmas's operation cursor): draws made while it lives are shown, at every display step, shifted to where the pointer is then (`platform::livePointer`: the mouse as the system has it, or under automation the last position given to the game), above everything else, so the cursor never trails the mouse. On Windows the pointer is asked of the system at each display frame (`cursorInClient`, any thread); elsewhere the system's mouse state is only as fresh as its last event pump, which the game does once a pass, so `show()` pumps the events before each display frame (they stay queued for the next pass; not when called from the event watch during a live resize, which is already inside SDL's pump).
- **Made at the finger, shown at once:** a draw marked with `platform::appearAtOnce` (AS2: every tool effect, `Shape::atFinger`, and the stitch thread) is shown as soon as the pass that made it has run, in its place in the drawing order, instead of when the display reaches that pass. A tool's flame, cream or thread thus keeps up with the pointer (in AS2 the system's, which moves at once) instead of trailing it by a pass; its look and its frames are untouched. `appearAtOnce(at)` also gives the time within the pass (0..1) the draw shows at: a trail laid along the finger's stroke since the last pass (AS2's `ITool::trail`) grows piece by piece as the display goes through the pass, each piece when the finger was there.
- **Tool trails** (blood, cream, fire while a tool is dragged) are the game's own splats, as in the original.
- Image draws sample half a texel inside their rectangle (`AdvancedImage`), so that drawn larger than 1:1 a region never blends with its neighbours in the texture (seams between pieces of one picture, fringes from other sheet cells or glyphs).
- Textures released by the game are deleted only once no frame that can still be shown uses them (`releaseTexture`): neither the game's newest two (debug shots) nor the display thread's.
- Screenshots (`AS_SHOT`, F2) replay the frame into a 1024×768 offscreen framebuffer, so they are display-independent; they wait for the texture thread's queued uploads first.
- **Checking motion:** `AS_FILM` logs where every draw lands at each display step of a range of passes (optionally saving the steps as images); `tools/motion_check.py` follows each drawn thing through such a log and reports stutter (move-stop-move), jumps and uneven speed, and `tools/motion_sweep.py` films every screen and every patient (played with the monkey test's strokes) and checks them all. `AS_DISPLAY_LOG` with `tools/display_pace.py` checks the display's own pace in real time (holds, jumps, missed refreshes).

## Reading the decompile

- `annotate.py` substitutes a local only when it is assigned exactly once. A reused local (Ghidra reuses them across branches) keeps its name, and each assignment carries a `/* $ivar */` or `/* @sel(...) */` label. Sends through such locals read `[obj <pcVar5>](args)`. An `*(int *)(self + *piVar1)` means the ivar named in `piVar1`'s most recent label on that code path.
- Start with `view.py`. Ghidra sometimes merges or drops calls (for example `[currentView load:0]` in `DispatchEventIntoView`), loses stack arguments (`/*args passed through*/`), or shows one shared tail call for two different selectors. When behavior looks missing or odd, check the instructions with `re/scripts/disasm.py <macho> <hex-address> <count>`, which labels literal-pool loads.
- Signs can hide in double constants: Ghidra prints `x / DAT_a * DAT_b` for a degree-to-radian conversion whose `DAT_b` may be **−π**. Always read such constants from `disrange.py`, which prints their values. This is how LargeCut's image placement and the battery's bolts came out mirrored.
- `in_r2`/`in_r3` are float arguments in core registers (soft-float ABI). `0x3f800000` is 1.0f. A "float" printed by the annotator for a literal may really be half of a double; read doubles with `struct.unpack('<d', …)` at file offset `address - 0x1000`.
